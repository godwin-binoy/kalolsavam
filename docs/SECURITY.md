# Security Architecture — Stagemaster & Manage Dashboards

## Threat Model (why this matters)

The public site is fully exposed: it lives in a **public Git repository** and is
served to every visitor's browser. Therefore:

1. **Nothing in the repo may contain secrets.** No passwords, no tokens, no
   session signing keys, no API URLs that imply hidden endpoints are "safe"
   because nobody knows them.
2. **Dashboards must assume attackers can see the code.** If `stagemaster/`
   and `manage/` were ever served publicly, they would reveal *where* and *how*
   to attack — so security must never rely on hiding them (no security by
   obscurity).
3. **Unauthenticated visitors must not be able to enumerate anything.** The
   public website only consumes published JSON snapshots; it never queries the
   live database or admin APIs.

## Core Design Decisions

### 1. Dashboards are NEVER served from the public web root
- The public site (GitHub Pages / CDN) contains **zero links** to `/stagemaster`
  or `/manage`. Their HTML files are excluded from the public build
  (`tools/build.py` strips them), so even the repo's deployed artifact doesn't
  advertise them.
- They are served **only by the on-premise server**, bound to the venue LAN
  (`--host 10.x.x.x` or `127.0.0.1` behind a reverse proxy), over **HTTPS with
  a locally-trusted certificate** (generated by `server/scripts/init_tls.py`,
  distributed to staff devices out-of-band via QR code).
- Network hardening: the server firewall rules (documented in
  `server/README.md`) expose only port 443 for the public snapshot API;
  dashboard routes additionally require authentication at the application
  layer, so even a misconfigured firewall cannot leak functionality.

### 2. Authentication: SRP-style password auth → short-lived JWT session
Plain `POST /login {password}` over HTTPS is acceptable, but we go further so
that **the password never crosses the wire**, even encrypted:

- **Argon2id** password hashes stored server-side (never plaintext, never MD5/SHA).
- Login uses a **challenge–response** flow (RFC 5054 SRP-6a, simplified):
  1. Client: `POST /api/auth/challenge {username}` → server returns `salt, B, session_id`
  2. Client derives shared secret locally, sends proof `M1`.
  3. Server verifies `M1`, returns verifier proof `M2` (mutual auth — client
     also verifies it's talking to the real server).
- On success the server issues:
  - **Access token**: signed `JWT (Ed25519)` — 15-minute lifetime, carries
    `role: stagemaster|admin`, `sid` (session id), `jti`.
  - **Refresh token**: single-use, 8-hour absolute expiry, rotated on every use
    (token family / reuse detection → whole family revoked if a stolen refresh
    token is replayed).
- Refresh token is delivered **HttpOnly + Secure + SameSite=Strict cookie**,
  path-scoped to `/api/auth/*` so the public site's JS can never read it.
- Access token lives only in memory (JS variable), never `localStorage`
  (XSS-resistant storage policy). CSP forbids inline scripts and external
  origins to reduce XSS token-theft surface.

### 3. Role separation & least privilege
| Role | Scope | Can do | Cannot do |
|---|---|---|---|
| `viewer` (public site) | none | GET `/api/public/*` snapshots/SSE | any mutation |
| `stagemaster` | one stage/venue | update run-of-show state, enter scores for assigned events | user mgmt, imports, deletes |
| `admin` (`manage`) | everything | CRUD master data, users, backups, deploy trigger | — |

Every mutating endpoint checks role **and** resource ownership
(e.g., stagemaster may only touch items whose `stage_id` is in their assignment).

### 4. Anti-bruteforce & anti-abuse
- Per-account exponential lockout (1m → 5m → 15m) after failed challenges.
- Per-IP token bucket rate limit on `/api/auth/*` (10/min).
- Mandatory TOTP second factor (RFC 6238) for `admin`; optional for stagemaster.
  Setup via scanned QR; codes validated ±1 window, single-use per time step
  (replay blocked).
- All auth events (success/failure/lockout/logout) written to an append-only
  audit log (`auth_audit` table) viewable in the manage dashboard.

### 5. Transport & headers
- TLS 1.2+ only, HSTS with preload, OCSP stapling where available.
- Response headers on all dashboard pages:
  `Content-Security-Policy: default-src 'self'; script-src 'self'; connect-src 'self'; frame-ancestors 'none'`
  `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY`,
  `Permissions-Policy: camera=(), microphone=(), geolocation=()`,
  `Cache-Control: no-store` on every authenticated response.
- CSRF: double-submit cookie + `X-Requested-With` requirement on mutations
  (defense-in-depth alongside SameSite=Strict).

### 6. Secrets & config handling
- `server/.env` holds `SESSION_SIGNING_SEED`, `DB_KEY`, etc. It is in
  `.gitignore` and **must never be committed**. A pre-commit secret scan
  blocks commits containing high-entropy strings / known key formats.
- First-run bootstrap: `python -m server.scripts.bootstrap_admin` generates a
  random one-time admin password, prints it once, forces change on first login.
- Key rotation: signing seed supports multiple active keys (`kid` header in
  JWT) so old tokens can be invalidated by removing a `kid`.

### 7. Session lifecycle
- Idle timeout 30 min (access token simply expires; silent refresh fails → UI
  shows re-login overlay). Absolute timeout 8 h.
- Logout revokes the refresh-token family server-side immediately.
- Admin can force-revoke any session from the manage dashboard ("active
  sessions" panel).

## What the public site sees
Only `GET /api/public/status.json` (or SSE stream) — pre-rendered, cached,
sanitized snapshots produced by the server from live data. No PII, no drafts,
no internal IDs beyond what is intentionally published.

### 8. URL unguessability (defense-in-depth, NOT the primary control)
Because the repo is public, dashboard paths (`/stagemaster`, `/manage`) and any
LAN port are visible to anyone reading the code. They are therefore treated as
**known** by attackers. Additional layers so knowledge of the URL gains nothing:
- **Application-layer auth**: every dashboard route and API mutation returns
  `401` without a valid session — a known path is inert.
- **Network-layer gating**: dashboards served only on the staff VLAN bind;
  `/api/admin/*` additionally IP-allowlisted (`ADMIN_IP_ALLOWLIST`).
- **Optional path secret**: `DASHBOARD_PATH_SALT` env var can suffix the
  mounted paths (e.g. `/stagemaster-7f3a`) purely to stop casual crawling /
  log noise — explicitly documented as *not* a security boundary.
- Rate limiting + lockouts make automated attacks against the known paths
  impractical even from inside the LAN.

## Remaining open questions

2. TOTP mandatory for stagemaster too, or admin-only?
3. Offline-first operation: should dashboards keep working if the LAN link to
   the server drops (queued writes flushed on reconnect)?
